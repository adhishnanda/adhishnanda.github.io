The problem

Business analysts ask questions about warehouse data in plain language. A naive text-to-SQL system generates SQL from the table schema alone, but it has no way to know that "average order value" means total revenue divided by order count at the order grain, not the average of line-item revenues. Without access to documented metric definitions, even a strong model like gpt-4o-mini gets metric-definition questions right only 50% of the time.

The copilot asked whether grounding SQL generation in a governed semantic layer, with retrieval, guardrails, and a retry loop, could close that gap.

The agent receives a natural-language question, retrieves relevant table documentation from a YAML semantic layer using hybrid retrieval with reranking, then builds a schema-grounded prompt so the LLM generates SQL only from retrieved definitions. The generated SQL passes through guardrails (SELECT-only enforcement, row limit, timeout) before executing on a read-only DuckDB warehouse loaded with TPC-H data. If execution fails, a validate-and-retry loop attempts correction up to twice. Every query, its generated SQL, execution result, and latency are logged via dlt for monitoring.

Guardrails

Every generated SQL statement passes through four checks before execution:

SELECT-only enforcement

Any statement that is not a pure SELECT query is rejected.

Row limit

Results are capped to prevent runaway queries.

Timeout

Queries that exceed a time limit are killed.

Validate-and-retry loop

If execution fails (syntax error, invalid column), the error message is fed back to the LLM for a second attempt (max 2 total). On the golden set, self-correction lifted accuracy from 84.0% to 86.0%, rescuing 1 of 4 triggered retries with zero regressions.

Without retrieval, gpt-4o-mini reinvents average_order_value as AVG(net_revenue) over line items (wrong grain: TPC-H orders average approximately 4 line items each). With retrieval, it uses the documented formula from the semantic layer and hits 100% on all 10 metric-definition questions.

What I would change

I would test with a larger golden set covering more edge cases (CTEs, window functions, nested subqueries). I would add a confidence score so the agent can flag low-confidence answers rather than presenting every result equally. And I would benchmark against newer open-weight models to reduce dependence on a paid API.
